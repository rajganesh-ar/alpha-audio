# ADR 0001 — Monorepo and toolchain

- Status: Accepted
- Date: 2026-10-14
- Task: `docs/tasks/0001-monorepo-skeleton.md`

## Context

The platform is one Payload 3 + Next.js application (storefront, admin, warehouse PWA) plus a separate dealer board, sharing pure business packages. We need one repository with typed boundaries, reproducible installs and the same gates locally and in CI.

## Decision

### Layout and tools

| Concern         | Choice                                                                      | Version    |
| --------------- | --------------------------------------------------------------------------- | ---------- |
| Runtime         | Node.js LTS, pinned in `.nvmrc`                                             | 22         |
| Package manager | pnpm workspaces, pinned in `package.json#packageManager`                    | 10.28.0    |
| Task runner     | Turborepo                                                                   | 2.11.8     |
| Application     | Payload, exact pin, all `@payloadcms/*` on the same version                 | 3.90.2     |
| Framework       | Next.js, exact pin (within Payload 3.90's peer range)                       | 16.4.0     |
| UI runtime      | React / React DOM, exact pin                                                | 19.2.4     |
| Database        | PostgreSQL 16 + pgvector, via `@payloadcms/db-postgres` (Drizzle bundled)   | 16         |
| Language        | TypeScript strict, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` | 5.9.3      |
| Tests           | Vitest (unit + integration projects), Testcontainers for local Postgres     | 4.1.11     |
| Lint / format   | ESLint 9 flat config + typescript-eslint strict + jsx-a11y; Prettier        | 9.39 / 3.9 |
| Env validation  | Zod schema in `packages/config/env.ts`, checked at startup                  | 3.25       |

The spec named Payload 3.89; 3.90.2 was the current 3.x release when the skeleton was built, so it is pinned instead. Upgrades are their own `chore(deps): payload 3.x` PR (CLAUDE.md).

Payload and the storefront run as one Next.js app in `apps/web`. Pure business logic lives in `packages/core`, `packages/acoustics` and `packages/llm`, which may not import React, Next.js or Payload UI.

### Decisions this task forced

1. **Pure-package lint rules are opt-in, not glob-matched.** The shared ESLint config first used a `files: ['packages/core/**', …]` block to ban React in pure packages. Flat-config globs resolve against the directory of the config file that loads them, so when ESLint ran inside `packages/core` the glob never matched and the rule silently did nothing. `@alpha/config/eslint` now exports `pure`, which `core`, `acoustics` and `llm` spread explicitly (`[...base, ...pure]`). `eslint-plugin-alpha/tests/boundaries.test.js` lints real source through both configs so a regression fails CI.

2. **The schema migration runs first; pgvector is the second migration.** The task asked for "migration 0001" to enable pgvector. Payload records each applied migration in `payload_migrations`, a table created by the generated schema migration, so a pgvector migration placed first runs and then fails to record itself. Order: `20261014_023806_initial_schema` (generated by `payload migrate:create`), then `20261014_023807_pgvector`. Without the generated schema migration, production (which boots from `prodMigrations`) would start with no tables at all; `next dev` hides this because it auto-pushes the schema.

3. **Turborepo task env is declared.** Turborepo 2 runs tasks in strict env mode and strips undeclared variables. `DATABASE_URL` and the app's env are listed per task in `turbo.json`, otherwise CI's database never reaches the integration tests and `next build` fails env validation.

4. **`NODE_ENV` is never set in `.env`.** Next.js and Vitest set it. A `NODE_ENV=development` line sourced before `next build` breaks prerendering (`useContext` of null on `/_global-error`). The env-example test forbids it.

5. **Generated files are excluded from Prettier.** `payload-types.ts`, the admin `importMap.js` and `src/migrations/` are written by Payload. CI regenerates the types and import map and fails if they differ from the commit; formatting them would make that check fail on every run.

6. **Integration tests live in `apps/web/tests/integration`, never in `src/migrations`.** `payload migrate` imports every file in the migrations folder as a migration.

## Consequences

- One install and one `pnpm check` cover the whole platform; CI runs the same commands.
- New pure packages must add `...pure` to their ESLint config.
- Every collection change ships a generated migration; dev push mode is a convenience, not a substitute.
- Local Postgres without Docker (as in the Claude Code cloud environment, where Docker Hub is blocked by egress policy) uses the distribution's pgvector package, currently 0.6.0, older than the `pgvector/pgvector:pg16` image CI uses. Nothing in P0 depends on newer pgvector features; revisit before the embeddings work in P3.
- The lockfile resolves `pg` at two versions: 8.20.0 inside the Payload adapter, 8.23.1 as `apps/web`'s own test dependency. The integration test hands Drizzle a connection string rather than a `pg.Client`, so the two never meet; consolidate when the adapter moves.
